S3 + API Gateway + Lambda (Python) + DynamoDB — tout déployé par Terraform sur LocalStack.

Objectif

En TP 3, Terraform déployait un site statique. Dans ce TP, on passe à une vraie application : un frontend HTML/JS qui permet à un utilisateur de s'inscrire et de se connecter, avec les données stockées dans une base DynamoDB. Toute la logique métier tourne dans des fonctions Lambda Python déclenchées via API Gateway.

Tout est déployé en une seule commande Terraform. Aucun serveur à gérer, aucune VM, aucune installation de base de données.

Ce que tu vas déployer : 13 ressources Terraform — une table DynamoDB, un rôle IAM, deux fonctions Lambda, une API Gateway avec 2 routes, et un bucket S3. En production AWS réelle, ce serait exactement la même architecture.

Serverless signifie qu'il n'y a aucun serveur à provisionner, patcher ou surveiller. Lambda exécute le code à la demande et s'arrête automatiquement. DynamoDB est entièrement managé. On ne paie (en production) que ce qu'on utilise réellement.

  • LocalStack démarré avec le token en variable d'environnement

  • AWS CLI installée — aws --version
  • Python 3.x — python --version (pour comprendre le code Lambda, pas besoin de l'exécuter localement)

2. Structure du projet

tp4-terraform-serverless/
├── main.tf # toute l'infrastructure Terraform
├── lambda/
│ ├── register.py # inscription : vérifie + stocke dans DynamoDB
│ └── login.py # connexion : vérifie email/password
├── frontend/
│ └── index.html.tpl # template HTML — l'URL de l'API est injectée par Terraform
└── .gitignore
Pourquoi .tpl ? Le fichier frontend contient un placeholder ${"{api_url}"} que Terraform remplace par l'URL réelle de l'API au moment du déploiement (via la fonction templatefile()). Ainsi le frontend connaît toujours l'URL correcte, même si l'ID de l'API change entre deux déploiements.

3. Comprendre main.tf

Ouvrir main.tf. Il contient 6 blocs principaux — lire chacun avant de déployer.

1
Provider — deux providers cette fois

Le provider aws est identique au TP 3, mais avec plus d'endpoints LocalStack. Un second provider archive est déclaré — c'est lui qui zippe les fichiers Python pour les envoyer à Lambda.

2
DynamoDB — la table users

Une seule ressource aws_dynamodb_table avec email comme clé primaire (type String). Le mode PAY_PER_REQUEST signifie qu'on ne provisionne pas de capacité en avance — on paie à l'utilisation.

resource "aws_dynamodb_table" "users" {
  name         = "users"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "email"
  attribute {
    name = "email"
    type = "S"
  }
}
3
IAM — le rôle d'exécution Lambda

Lambda a besoin d'un rôle IAM pour savoir ce qu'il a le droit de faire. Ici : uniquement GetItem et PutItem sur la table users. C'est le principe du least privilege — on n'accorde que le minimum nécessaire.

4
Lambda — packaging et déploiement

Terraform zippe automatiquement les fichiers .py via le provider archive, puis les envoie à LocalStack. Le source_code_hash permet de détecter les modifications du code Python et de redéployer uniquement si nécessaire.

5
API Gateway — les routes HTTP

L'API expose deux routes : POST /register et POST /login. Chaque route est composée de 3 ressources Terraform : une ressource (le chemin URL), une méthode (POST), et une intégration (AWS_PROXY → Lambda). Le type AWS_PROXY passe la requête HTTP brute à Lambda sans transformation.

6
S3 + templatefile — le frontend intelligent

Terraform utilise la fonction templatefile() pour injecter l'URL de l'API dans le HTML avant de l'uploader dans S3. Ainsi const API_URL = "${"{api_url}"}" dans le template devient const API_URL = "https://abc123.execute-api.localhost.localstack.cloud:4566/dev" dans le fichier final.

C'est un pattern courant en IaC : les fichiers de configuration dépendent de ressources créées dynamiquement (IDs, URLs, ARNs). templatefile() résout cette dépendance proprement.

5. Tester l'application

1
Ouvrir le frontend

Copier la valeur de frontend_url dans le navigateur :

https://localhost.localstack.cloud:4566/auth-frontend/index.html

Le formulaire d'inscription doit s'afficher.

2
S'inscrire

Entrer un email et un mot de passe → cliquer S'inscrire. Si tout fonctionne, l'interface passe en état "Connecté" et affiche le token de session.

Le token est un identifiant de session généré aléatoirement (64 caractères hexadécimaux), stocké dans sessionStorage côté navigateur.
3
Vérifier dans DynamoDB

Dans le Resource Browser de LocalStack → DynamoDB → table users → explorer les items. L'utilisateur créé doit apparaître avec son email, son password_hash et son session_token.

Observer que le mot de passe n'est jamais stocké en clair — uniquement son empreinte SHA-256. C'est une règle fondamentale de sécurité.
4
Tester via CLI — appel direct à l'API

On peut aussi tester les endpoints directement avec la CLI, sans passer par le frontend :

# Inscription (remplacer <api_id> par la valeur affichée dans les outputs)
aws --endpoint-url=http://localhost:4566 --no-sign-request `
    apigateway get-rest-apis

# Ou tester directement avec curl
curl -X POST https://<api_id>.execute-api.localhost.localstack.cloud:4566/dev/register `
    -H "Content-Type: application/json" `
    -d '{"email":"test@exemple.com","password":"motdepasse123"}'
5
Se déconnecter et se reconnecter

Cliquer Se déconnecter, puis aller sur l'onglet Connexion et entrer les mêmes identifiants. Le token doit être le même qu'à l'inscription.

Tester avec un mauvais mot de passe : le message "Email ou mot de passe incorrect" doit s'afficher.

6. Modifier le code Lambda et re-déployer

Modifier lambda/register.py : ajouter un champ created_at lisible dans le message de retour.

Dans la fonction, trouver le bloc return final et ajouter "created_at" :

return {
    "statusCode": 201,
    "headers": HEADERS,
    "body": json.dumps({
        "message": "Inscription réussie",
        "email": email,
        "token": token,
        "created_at": datetime.utcnow().isoformat(),  # ajout
    }),
}

Puis re-déployer :

terraform apply
Terraform détecte que le fichier Python a changé (via le hash SHA256), recrée l'archive ZIP et redéploie uniquement la fonction register.

7. Nettoyer

terraform destroy

Les 13 ressources sont supprimées en une commande. Confirmer avec yes.

En production, destroy supprime aussi les données DynamoDB. Toujours faire une sauvegarde avant de détruire un environnement qui contient des données réelles.

Réflexion

Question 1 — Serverless vs serveur traditionnel

Dans cette architecture, qui démarre et arrête les fonctions Lambda ? Que se passe-t-il si 1000 utilisateurs se connectent simultanément ?

Question 2 — IAM et least privilege

Le rôle Lambda n'autorise que GetItem et PutItem sur la table users. Que se passerait-il si le code Lambda tentait de faire un Scan (lire toute la table) ou de supprimer un item ?

Question 3 — templatefile et dépendances dynamiques

Pourquoi ne peut-on pas simplement mettre l'URL de l'API en dur dans index.html ? Qu'est-ce qui change entre deux déploiements ?

Question 4 — Limites de sécurité

Ce TP utilise SHA-256 pour hacher les mots de passe. En production, pourquoi préférerait-on bcrypt ou argon2 ? Quelle autre limite de sécurité vois-tu dans cette implémentation ?

Corrigé

Question 1 — Serverless

AWS (ou LocalStack) démarre et arrête les instances Lambda automatiquement. Chaque requête peut déclencher une nouvelle instance Lambda. Si 1000 utilisateurs se connectent simultanément, AWS lance jusqu'à 1000 instances Lambda en parallèle — sans aucune configuration de notre part. C'est la scalabilité automatique du serverless. En retour, on perd le contrôle sur l'environnement d'exécution et la persistance en mémoire entre deux invocations.

Question 2 — IAM et least privilege

La requête serait refusée avec une erreur AccessDeniedException. IAM évalue toutes les actions et refuse par défaut tout ce qui n'est pas explicitement autorisé. C'est le principe du least privilege : si une fonction Lambda est compromise, l'attaquant ne peut faire que ce que le rôle autorise. Ici, il pourrait lire et écrire des items, mais pas scanner toute la table, ni la supprimer, ni accéder à d'autres services.

Question 3 — templatefile

L'ID de l'API Gateway est généré aléatoirement par AWS (ou LocalStack) à chaque création. Si on détruit et recrée l'infrastructure, l'ID change et l'URL change. Le frontend hardcodé serait alors cassé. templatefile() résout ce problème en injectant l'URL réelle au moment du déploiement — le frontend est toujours cohérent avec l'infrastructure.

Question 4 — Sécurité des mots de passe

SHA-256 est rapide — c'est un avantage pour le hachage de fichiers, mais un inconvénient pour les mots de passe : un attaquant peut tester des milliards de combinaisons par seconde avec du matériel GPU. bcrypt et argon2 sont délibérément lents et configurables en difficulté — ils résistent aux attaques par force brute. Autre limite : l'absence de "sel" (valeur aléatoire ajoutée avant le hachage) rend les hashes identiques pour deux utilisateurs ayant le même mot de passe, ce qui facilite les attaques par tables arc-en-ciel.
