Contexte

Dans le cours du matin, le TP proposait deux options pour déployer une application web :

  • Option 1 : Vercel — rapide, sans infrastructure à gérer
  • Option 2 : AWS S3 Static Website — plus proche du monde professionnel, mais nécessite un compte AWS réel

Aujourd'hui on réalise l'Option 2 en local grâce à LocalStack, un outil qui émule les services AWS sur ta machine. Même workflow, mêmes concepts, mêmes API — mais zéro compte AWS, zéro risque de coût, tout en local.

☁️ AWS réel (Option 2 originale)

  • Compte AWS requis (carte bancaire)
  • Bucket créé sur les serveurs Amazon
  • URL publique mondiale
  • Facturation à l'usage
  • 12 mois gratuits (Free Tier)

🖥 LocalStack (ce TP)

  • Aucun compte AWS
  • Bucket créé sur ta machine (Docker)
  • URL locale : localhost.localstack.cloud:4566
  • Totalement gratuit, sans limite
  • Identique à 95% à AWS réel
Ce que tu vas apprendre : créer un bucket S3, désactiver le blocage des accès publics, activer le Static Website Hosting, uploader des fichiers HTML/CSS, et accéder au site via son URL. Ce sont exactement les étapes d'un déploiement S3 professionnel.

1. Prérequis

Avant de commencer ce TP, les éléments suivants doivent être en place :

  • Docker Desktop installé et démarré (icône baleine visible dans la barre des tâches)
  • Un compte LocalStack gratuit (plan Hobby) créé sur app.localstack.cloud
  • Un Auth Token LocalStack récupéré dans Workspace → Auth Tokens
  • La variable d'environnement LOCALSTACK_AUTH_TOKEN définie dans ton terminal
👉 Si l'un de ces points n'est pas encore fait, se reporter à l'Annexe – Installation de l'environnement en début de document. Elle couvre Windows, macOS et Linux, avec les commandes de vérification et la résolution des problèmes courants.

2. Démarrer LocalStack

Si ce n'est pas déjà fait, définir d'abord la variable d'environnement avec ton token (voir Annexe B) :

# Windows PowerShell
$env:LOCALSTACK_AUTH_TOKEN = "ls-XXXXX"

# macOS / Linux
export LOCALSTACK_AUTH_TOKEN="ls-XXXXX"

Puis lancer LocalStack — Docker lit automatiquement la variable depuis ton environnement :

docker run --rm -p 4566:4566 -e LOCALSTACK_AUTH_TOKEN localstack/localstack
Le -e LOCALSTACK_AUTH_TOKEN sans valeur explicite dit à Docker : "prends la valeur depuis l'environnement du host". Le token ne s'affiche nulle part dans la commande.
Que fait cette commande ?
  • -p 4566:4566 : expose le port 4566 (point d'entrée unique de tous les services AWS émulés)
  • -e LOCALSTACK_AUTH_TOKEN : sans =, Docker lit directement la variable d'environnement du host qui porte exactement ce nom et l'injecte dans le conteneur — le token ne s'écrit nulle part dans la commande
  • localstack/localstack : l'image Docker officielle LocalStack
LocalStack est prêt quand les logs affichent : 
Ready.
Premier démarrage = téléchargement de l'image (~600 Mo), peut prendre 1–2 min.
Important : laisser ce terminal ouvert pendant tout le TP. LocalStack s'arrête si on ferme le terminal ou si on fait Ctrl+C.

Cas multi-comptes : choisir explicitement quel token utiliser

Si tu as plusieurs comptes LocalStack (par exemple un compte formation, un compte perso, un compte client), nomme tes variables pour les distinguer :

# Windows PowerShell — définir plusieurs tokens
$env:LOCALSTACK_TOKEN_FORMATION = "ls-XXXXX"   # compte formation
$env:LOCALSTACK_TOKEN_PERSO     = "ls-YYYYY"   # compte personnel
$env:LOCALSTACK_TOKEN_CLIENT    = "ls-ZZZZZ"   # compte client

# macOS / Linux
export LOCALSTACK_TOKEN_FORMATION="ls-XXXXX"
export LOCALSTACK_TOKEN_PERSO="ls-YYYYY"
export LOCALSTACK_TOKEN_CLIENT="ls-ZZZZZ"

Puis passer explicitement le token voulu au lancement :

# Windows PowerShell — lancer avec le token "formation"
docker run --rm -p 4566:4566 -e LOCALSTACK_AUTH_TOKEN=$env:LOCALSTACK_TOKEN_FORMATION localstack/localstack

# macOS / Linux
docker run --rm -p 4566:4566 -e LOCALSTACK_AUTH_TOKEN=$LOCALSTACK_TOKEN_FORMATION localstack/localstack
C'est la seule situation où l'on met une valeur explicite après le = dans -e — et cette valeur est une variable, jamais le token brut écrit en clair.

Vérification

Dans un autre terminal, tester :

curl http://localhost:4566/_localstack/health

On doit obtenir une réponse JSON avec "running": true.

3. Ouvrir l'interface web

1
Aller sur app.localstack.cloud

Dans le navigateur, ouvrir app.localstack.cloud et se connecter avec son compte.

2
Vérifier que l'instance est active (point vert)

Dans le menu de gauche, sous Instances, l'entrée localhost.localstack.cloud doit afficher un point ● vert. Si le point est gris ou absent, LocalStack n'est pas démarré ou le token est incorrect.

Instance grise malgré un LocalStack démarré : vérifier que le token passé à docker run correspond bien au compte connecté sur app.localstack.cloud.
Renommer l'instance : oui, c'est possible. Cliquer sur le nom de l'instance puis sur les ··· (trois points) à droite de l'en-tête → Rename. Utile si tu as plusieurs instances pour les distinguer (ex: Formation-2CLD3, Projet-Client…).
3
Accéder au Resource Browser

Il n'y a pas d'entrée "Resource Browser" dans le menu de gauche. Pour y accéder : cliquer sur le nom de l'instance (localhost.localstack.cloud) dans la liste des Instances. L'onglet Resource Browser s'active automatiquement dans la partie principale et affiche la liste de tous les services AWS émulés.

4
Naviguer vers S3

Dans la liste des services, faire défiler jusqu'à la section Storage et cliquer sur S3. La vue affiche la liste des buckets ("No rows" pour l'instant — c'est normal).

4. Créer le bucket S3

1
Cliquer sur "Create"

Dans la vue Buckets, cliquer sur le bouton Create (en haut à gauche, à côté de l'icône de refresh). Un formulaire s'ouvre avec plusieurs champs :

  • ACL : laisser vide pour l'instant (on gèrera les permissions via une Bucket Policy)
  • Bucket (obligatoire) : saisir mon-site-web-demo
  • Location Constraint : laisser vide → le bucket sera créé en us-east-1 par défaut
  • Grant Full Control / Grant Read / … : laisser tous ces champs vides

Cliquer sur Submit pour créer le bucket.

Règles AWS de nommage : 3 à 63 caractères, minuscules, chiffres et tirets uniquement, pas de points ni de majuscules, unique mondialement dans AWS réel. Sur LocalStack, l'unicité est locale à ta machine.
Le bucket est créé et visible dans la liste. On peut directement passer à l'upload.
LocalStack vs AWS réel : sur AWS réel, chaque bucket est privé par défaut et un paramètre "Block all public access" protège contre toute exposition accidentelle — il faudrait le désactiver explicitement pour héberger un site public. Sur LocalStack, cette protection n'existe pas dans l'interface : les objets sont accessibles directement via leur URL dès l'upload. C'est une simplification pour le développement local.

3
Uploader les fichiers dans le bucket

Dans le Resource Browser → bucket mon-site-web-demo → bouton Upload. Uploader les deux fichiers : index.html et error.html.

L'interface web ne définit pas le Content-Type des fichiers. Le navigateur peut alors télécharger le fichier au lieu de l'afficher. Préférer la CLI ci-dessous pour garantir le bon type MIME.

Alternative CLI (recommandée) — répéter pour chaque fichier à uploader :

# Windows PowerShell
aws --endpoint-url=http://localhost:4566 `
    s3 cp "2CLD3P - initiation aux clouds/<fichier>.html" `
    s3://mon-site-web-demo/<fichier>.html `
    --content-type "text/html" `
    --no-sign-request `
    --region us-east-1

# macOS / Linux
aws --endpoint-url=http://localhost:4566 \
    s3 cp "2CLD3P - initiation aux clouds/<fichier>.html" \
    s3://mon-site-web-demo/<fichier>.html \
    --content-type "text/html" \
    --no-sign-request \
    --region us-east-1
Remplacer <fichier> par le nom réel : index puis error. Le chemin source correspond au dossier 2CLD3P - initiation aux clouds/ présent dans le repo.
Les deux fichiers doivent apparaître à la racine du bucket. Vérifier qu'ils ne sont pas dans un sous-dossier.

6. Tester le site

1
Accéder au site via le navigateur

Sur LocalStack, l'URL d'accès à un objet S3 est :

http://localhost:4566/mon-site-web-demo/index.html

Ouvrir cette URL dans le navigateur. La page HTML doit s'afficher.

Pourquoi le HTML s'affiche-t-il et ne se télécharge-t-il pas ? Parce que tu as uploadé tes fichiers avec --content-type "text/html" via la CLI. Le navigateur reçoit l'en-tête HTTP Content-Type: text/html et affiche le HTML directement. Sans cet en-tête (upload via l'interface web), le navigateur ne sait pas que c'est du HTML et propose de télécharger le fichier.
🎉 Si la page s'affiche correctement : ton site est "hébergé" sur S3 local. Même principe en production AWS réelle — seule l'URL change.
2
Tester une URL inexistante

Accéder à une URL qui n'existe pas :

http://localhost:4566/mon-site-web-demo/page-inexistante.html

LocalStack retourne un XML d'erreur brut (NoSuchKey) — c'est le comportement attendu. Sans Static Website Hosting configuré, il n'y a aucun mécanisme pour rediriger vers error.html.

Sur AWS réel, en activant le Static Website Hosting avec un "Error document" défini sur error.html, S3 retournerait ta page d'erreur personnalisée à la place du XML. C'est une des différences concrètes entre LocalStack (émulation simplifiée) et la production.
3
Faire une modification et re-déployer

Modifier le texte de index.html sur ta machine (changer le titre, la couleur, ajouter un paragraphe), re-uploader le fichier, puis recharger la page dans le navigateur.

C'est ainsi que fonctionne un déploiement S3 : il suffit de remplacer le fichier. Pas de redémarrage de serveur, pas de déploiement applicatif.

🏁 Résultat final attendu

  • Un bucket S3 nommé mon-site-web-demo visible dans le Resource Browser
  • Deux fichiers index.html et error.html uploadés
  • Le site accessible sur http://localhost:4566/mon-site-web-demo/index.html
  • Compréhension des étapes : bucket → permissions → policy → upload → URL

Indices (si vous êtes bloqués)

Indice 1 — Si l'interface affiche "Network Failure" : LocalStack n'est pas démarré, ou a planté. Vérifier les logs dans le terminal avec docker ps et redémarrer si besoin.
Indice 2 — Si la page affiche un XML AccessDenied : la Bucket Policy n'est pas correctement enregistrée. Revérifier la section 5 (étape 3) et t'assurer que le nom du bucket dans le Resource correspond exactement à celui que tu as créé.
Indice 3 — Si la page ne s'affiche pas du tout : vérifier que le fichier est bien à la racine du bucket (pas dans un sous-dossier), et que l'URL ne contient pas de majuscule ni d'espace.
Rappel : sur LocalStack gratuit, le Static Website Hosting avec redirection automatique vers index.html peut se comporter différemment d'AWS réel. Utiliser l'URL complète avec /index.html pour ce TP.

Pour aller plus loin (si vous avez du temps)

  • Ajouter un fichier CSS externe : créer un fichier style.css, l'uploader dans le bucket, et le référencer depuis index.html. Vérifier que le CSS est bien chargé.
  • Organiser en sous-dossiers : créer un dossier assets/ dans le bucket, y uploader une image, et l'afficher dans la page HTML.
  • Comparer avec AWS réel : repérer, dans les étapes que tu viens de faire, ce qui serait différent avec un vrai compte AWS. (Réponse : URL en .s3-website.amazonaws.com, confirmation de désactivation du blocage public plus stricte, etc.)
  • Réfléchir à CloudFront : en production, comment ferait-on pour que ce site soit accessible via https://www.monentreprise.com ? Chercher ce que font AWS CloudFront et Route 53.

Corrigé et réflexions professionnelles

Pourquoi S3 pour un site statique ?

En production, héberger un site statique sur S3 est une pratique courante et économique : pas de serveur web à maintenir, scalabilité automatique, durabilité très élevée (99,999999999% — soit statistiquement 1 objet perdu pour 10 millions stockés, sur 10 000 ans, grâce à la réplication automatique sur au moins 3 datacenters distincts), coût très bas (quelques centimes par mois pour un petit site), et intégration native avec CloudFront pour la distribution mondiale et HTTPS.

Les limites : pas d'exécution de code côté serveur, pas de session utilisateur, pas de base de données. Pour un site dynamique, on combine S3 (fichiers statiques) + Lambda (logique serveur) + API Gateway (routing) + DynamoDB (données).

Que signifie la Bucket Policy qu'on a écrite ?

ChampValeurSignification
EffectAllowAutoriser (≠ Deny)
Principal*Tout le monde (anonyme ou connecté)
Actions3:GetObjectUniquement la lecture d'objet (pas l'upload, pas la suppression)
Resourcearn:aws:s3:::mon-site-web-demo/*Tous les objets du bucket (le /* est important)

En production, on irait plus loin : restreindre l'accès à CloudFront uniquement (Origin Access Control), ajouter du chiffrement, des logs d'accès, et une policy refusant explicitement les accès non chiffrés.

Valeur de LocalStack pour un professionnel

LocalStack permet de développer et tester du code AWS sans compte réel. Cas d'usage professionnels : CI/CD offline (les tests d'intégration tournent sans accès réseau), développement en avion ou sans VPN, test des permissions IAM avant déploiement en production, formation sans contrainte de compte. Des outils comme Terraform, boto3 ou l'AWS CLI fonctionnent identiquement avec LocalStack — il suffit de changer l'URL d'endpoint.

B. Créer son compte LocalStack

1
S'inscrire sur app.localstack.cloud
  1. Aller sur app.localstack.cloud/sign-up.
  2. Créer un compte avec un email et un mot de passe. Confirmer l'email si demandé.
  3. Sélectionner le plan Hobby (gratuit, pas de carte bancaire).
Le plan Hobby donne accès au Resource Browser (interface web), à l'instance locale et aux services de base dont S3, Lambda, DynamoDB, IAM.
2
Récupérer son Auth Token et le stocker en variable d'environnement
  1. Une fois connecté, cliquer sur Workspace dans le menu de gauche.
  2. Aller dans Auth Tokens.
  3. Cliquer sur Create Token, lui donner un nom (ex: formation-2cld3).
  4. Copier le token généré (commence par ls-). Le noter dans un endroit sûr — il ne sera plus affiché après fermeture de la page.

Stocker le token dans une variable d'environnement — ne jamais l'écrire en dur dans une commande :

Windows (PowerShell) — session courante :

$env:LOCALSTACK_AUTH_TOKEN = "ls-XXXXX"

Windows (PowerShell) — persistant pour ton compte utilisateur :

[Environment]::SetEnvironmentVariable("LOCALSTACK_AUTH_TOKEN", "ls-XXXXX", "User")

Ou ouvrir directement le gestionnaire graphique de variables d'environnement sans droits administrateur :

rundll32 sysdm.cpl,EditEnvironmentVariables

macOS / Linux — session courante :

export LOCALSTACK_AUTH_TOKEN="ls-XXXXX"

macOS / Linux — persistant (dans ~/.bashrc ou ~/.zshrc) :

echo 'export LOCALSTACK_AUTH_TOKEN="ls-XXXXX"' >> ~/.zshrc
source ~/.zshrc
Pourquoi ne pas écrire le token en dur ? Un secret écrit directement dans une commande apparaît dans l'historique du terminal (history), dans les logs Docker, et risque d'être copié dans un script ou un fichier versionné. Stocker les secrets dans des variables d'environnement est la pratique standard en DevOps.

🧹 Annexe 2 – Suppression et nettoyage des ressources

Supprimer proprement ses ressources est un réflexe professionnel essentiel. Sur LocalStack, c'est optionnel (tout disparaît à l'arrêt du conteneur). Sur AWS réel, c'est indispensable : les ressources non supprimées continuent de tourner et de générer des coûts.

A. Supprimer les ressources S3 (CLI)

1
Vider le bucket

Un bucket S3 ne peut pas être supprimé s'il contient encore des objets. Il faut d'abord les supprimer tous :

# Windows PowerShell
aws --endpoint-url=http://localhost:4566 `
    s3 rm s3://mon-site-web-demo --recursive `
    --no-sign-request

# macOS / Linux
aws --endpoint-url=http://localhost:4566 \
    s3 rm s3://mon-site-web-demo --recursive \
    --no-sign-request

Le flag --recursive supprime tous les objets du bucket en une seule commande.

2
Supprimer le bucket
aws --endpoint-url=http://localhost:4566 s3 rb s3://mon-site-web-demo --no-sign-request

rb = remove bucket. Le bucket doit être vide, sinon la commande échoue.

Vérifier la suppression : aws --endpoint-url=http://localhost:4566 s3 ls --no-sign-request — le bucket ne doit plus apparaître.

B. Arrêter LocalStack

3
Arrêter le conteneur

Dans le terminal où LocalStack tourne, faire Ctrl+C. Grâce au flag --rm utilisé au lancement, le conteneur se supprime automatiquement — et avec lui toutes les ressources encore présentes.

Vérifier que le conteneur est bien arrêté :

docker ps

Aucun conteneur localstack ne doit apparaître.

C. LocalStack vs AWS réel — une différence fondamentale

LocalStackAWS réel
Arrêter le conteneur / la session Toutes les ressources disparaissent Les ressources continuent d'exister (et de coûter)
Oubli de suppression Sans conséquence Facture qui s'accumule silencieusement
Bonne pratique Supprimer quand même pour prendre l'habitude Supprimer obligatoirement après chaque TP / projet test
Cas réel : une startup a laissé tourner une instance EC2 m5.8xlarge (32 vCPU) allumée par erreur pendant un mois → 4 800 € de surcoût. Le réflexe "je supprime ce que je n'utilise plus" s'acquiert dès la formation.

D. Aller plus loin — nettoyage automatique sur AWS réel

En production, on ne supprime pas à la main. On automatise :

  • AWS Budgets + alertes : notification dès qu'une dépense dépasse un seuil
  • Lifecycle policies S3 : suppression automatique des objets après N jours
  • Terraform destroy : supprime toute l'infrastructure décrite dans le code en une commande
  • AWS Cost Explorer : visualiser les ressources qui coûtent, détecter les oublis
