Contexte – Pourquoi Terraform ?

En TP 2, tu as créé le bucket S3 à la main via l'interface web, puis uploadé les fichiers via la CLI. Ça fonctionne — mais imagine devoir refaire ça pour 10 environnements, ou expliquer à un collègue exactement ce que tu as configuré.

🖱 TP 2 — Manuel

  • Clics dans l'interface web
  • Commandes CLI une par une
  • Non reproductible automatiquement
  • Difficile à versionner
  • Erreur possible à chaque étape

🟣 TP 3 — Terraform (IaC)

  • Infrastructure décrite dans des fichiers texte
  • Une commande pour tout créer
  • Reproductible à l'identique
  • Versionnable dans Git
  • Terraform vérifie avant d'agir
Infrastructure as Code (IaC) : l'idée est simple — décrire l'infrastructure souhaitée dans des fichiers, comme on écrit du code. Terraform lit ces fichiers et crée (ou modifie, ou supprime) les ressources pour correspondre à ce qui est décrit. Si le fichier ne change pas, Terraform ne fait rien.
terraform init
→
terraform plan
→
terraform apply
→
terraform destroy

Ce workflow en 4 commandes est le même en dev local, en CI/CD et en production.

1. Prérequis

  • Terraform installé — vérifier : terraform --version
  • LocalStack démarré avec le token en variable d'environnement (cf. TP 2)
  • AWS CLI installée — vérifier : aws --version
  • Git installé et configuré avec le bon compte GitHub
Repo GitHub du TP : les fichiers de départ sont disponibles sur github.com/mentiforjastudio-svg/2CLD3---introduction-au-Cloud.

git clone https://github.com/mentiforjastudio-svg/2CLD3---introduction-au-Cloud.git

Tu obtiens directement main.tf, index.html et error.html — prêts à l'emploi.

2. Structure du projet

Créer un nouveau dossier dédié à ce TP, par exemple tp3-terraform-s3, et y placer les fichiers suivants :

tp3-terraform-s3/
├── main.tf # configuration Terraform (à créer)
├── index.html # copié depuis le TP 2
└── error.html # copié depuis le TP 2
Convention Terraform : un projet minimal tient dans un seul fichier main.tf. En production, on sépare en variables.tf, outputs.tf, providers.tf… mais pour ce TP un seul fichier suffit et reste lisible.

Après un terraform init et terraform apply, Terraform créera automatiquement :

tp3-terraform-s3/
├── main.tf
├── index.html
├── error.html
├── .terraform/ # plugins téléchargés (ne pas versionner)
├── .terraform.lock.hcl # versions verrouillées des providers
└── terraform.tfstate # état de l'infrastructure (ne pas supprimer !)

3. Configurer le provider AWS pour LocalStack

Créer le fichier main.tf et y coller le bloc suivant. C'est la configuration du provider — il indique à Terraform quel cloud cibler et comment s'y connecter.

# main.tf — TP 3 : S3 Static Website via Terraform + LocalStack

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  # Credentials fictives — LocalStack ne les vérifie pas
  access_key = "test"
  secret_key = "test"
  region     = "us-east-1"

  # Désactiver les vérifications AWS qui ne s'appliquent pas à LocalStack
  skip_credentials_validation = true
  skip_metadata_api_check     = true
  skip_requesting_account_id  = true

  # Forcer le style path pour S3 : localhost:4566/bucket (au lieu de bucket.localhost)
  s3_use_path_style = true

  # Pointer tous les appels S3 vers LocalStack
  endpoints {
    s3 = "http://localhost:4566"
  }
}
Ces paramètres sont spécifiques à LocalStack. Sur AWS réel, on n'utilise jamais access_key = "test" ni skip_credentials_validation. Le provider détecterait automatiquement les credentials depuis les variables d'environnement ou les profils AWS CLI.
Qu'est-ce qu'un provider Terraform ? C'est un plugin qui sait parler à une API spécifique (AWS, Azure, GCP, GitHub, Kubernetes…). Le provider hashicorp/aws connaît toutes les ressources AWS et traduit le code HCL en appels d'API. Terraform le télécharge automatiquement lors du terraform init.

4. Déclarer les ressources S3

Ajouter à la suite du provider dans main.tf les trois ressources suivantes :

# --- Ressource 1 : le bucket S3 ---
resource "aws_s3_bucket" "site" {
  bucket = "mon-site-tf-demo"
}

# --- Ressource 2 : le fichier index.html ---
resource "aws_s3_object" "index" {
  bucket       = aws_s3_bucket.site.id   # référence la ressource ci-dessus
  key          = "index.html"
  source       = "${path.module}/index.html"
  content_type = "text/html"
  etag         = filemd5("${path.module}/index.html")  # détecte les modifications
}

# --- Ressource 3 : le fichier error.html ---
resource "aws_s3_object" "error" {
  bucket       = aws_s3_bucket.site.id
  key          = "error.html"
  source       = "${path.module}/error.html"
  content_type = "text/html"
  etag         = filemd5("${path.module}/error.html")
}
Points de syntaxe à retenir :
  • resource "type" "nom_local" — le type est imposé par AWS, le nom local sert à référencer la ressource dans le reste du fichier
  • aws_s3_bucket.site.id — référence la propriété id du bucket créé ci-dessus ; Terraform résout automatiquement les dépendances
  • etag = filemd5(...) — calcule l'empreinte MD5 du fichier local ; si le fichier change, Terraform le détecte et re-uploade l'objet
  • ${path.module} — chemin du répertoire contenant le main.tf

5. Le workflow Terraform : init → plan → apply

1
terraform init — initialiser le projet

Dans un terminal, se placer dans le dossier tp3-terraform-s3 puis lancer :

cd tp3-terraform-s3
terraform init

Terraform télécharge le provider hashicorp/aws et crée le dossier .terraform/. À ne faire qu'une fois par projet (ou après avoir modifié les providers).

Résultat attendu : Terraform has been successfully initialized!
2
terraform plan — prévisualiser sans rien créer
terraform plan

Terraform compare l'état souhaité (le code) avec l'état réel (le tfstate, vide pour l'instant) et affiche ce qu'il va faire — sans le faire.

Résultat attendu : 3 ressources à créer (+ create) 
Plan: 3 to add, 0 to change, 0 to destroy.
C'est ici que réside la valeur du plan : en production, on fait toujours un plan avant d'appliquer — pour vérifier qu'on ne va pas détruire accidentellement quelque chose d'important.
3
terraform apply — créer les ressources
terraform apply

Terraform affiche à nouveau le plan et demande une confirmation. Taper yes pour confirmer.

Do you want to perform these actions? (yes/no): yes
Résultat attendu : 
Apply complete! Resources: 3 added, 0 changed, 0 destroyed.
Pour éviter la confirmation interactive (utile en CI/CD) : terraform apply -auto-approve.

6. Tester le résultat

1
Vérifier via le navigateur

Ouvrir dans le navigateur :

https://localhost.localstack.cloud:4566/mon-site-tf-demo/index.html
La même page qu'en TP 2 doit s'afficher — mais cette fois créée par Terraform.
2
Vérifier via le Resource Browser

Dans app.localstack.cloud → instance → S3 : le bucket mon-site-tf-demo doit être visible avec ses deux objets.

3
Observer le fichier terraform.tfstate

Ouvrir le fichier terraform.tfstate dans un éditeur de texte. C'est un fichier JSON qui décrit exactement ce que Terraform sait avoir créé : le bucket, ses propriétés, les deux objets et leurs métadonnées.

Le tfstate est la mémoire de Terraform. Si on le supprime, Terraform ne sait plus que le bucket existe et tentera de tout recréer — même si le bucket existe déjà dans LocalStack. Ne jamais le supprimer manuellement.

7. Modifier et re-déployer

C'est ici que l'IaC montre tout son intérêt. On va modifier index.html et observer comment Terraform détecte et applique le changement.

1
Modifier index.html

Dans index.html, changer le titre ou la couleur de fond. Sauvegarder.

2
Relancer terraform plan
terraform plan

Terraform calcule le nouveau MD5 du fichier, le compare à celui stocké dans le tfstate, et détecte que l'objet a changé.

Résultat attendu : 
Plan: 0 to add, 1 to change, 0 to destroy.
Seul index.html est marqué ~ update in-place.
3
Appliquer et vérifier
terraform apply

Confirmer avec yes, puis recharger la page dans le navigateur. La modification s'affiche.

Idempotence : si on relance terraform apply sans rien changer, Terraform répond No changes. Infrastructure is up-to-date. Il ne recrée pas ce qui existe déjà. C'est une propriété fondamentale de l'IaC — safe à rejouer autant de fois qu'on veut.

8. Nettoyer avec terraform destroy

1
Détruire toutes les ressources
terraform destroy

Terraform liste les ressources qu'il va supprimer et demande confirmation. Taper yes.

Résultat attendu : 
Destroy complete! Resources: 3 destroyed.
2
Vérifier la suppression

Tenter d'accéder à https://localhost.localstack.cloud:4566/mon-site-tf-demo/index.html → le bucket n'existe plus, S3 retourne une erreur XML.

Vérifier aussi dans le Resource Browser : la liste des buckets est vide.

Sur AWS réel, terraform destroy supprime toutes les ressources décrites dans le code — y compris des bases de données, des instances EC2, des données. Toujours vérifier le plan avant de confirmer, surtout en production. En environnement de TP ou de développement, c'est au contraire une commande précieuse pour ne pas oublier de ressources allumées.

Réflexion – Ce que Terraform change vraiment

Question 1

On a obtenu le même résultat qu'en TP 2 (bucket S3 + fichiers uploadés avec le bon Content-Type). Quelle est la différence fondamentale dans la façon d'y arriver ?

Question 2

Dans le main.tf, la ressource aws_s3_object.index contient bucket = aws_s3_bucket.site.id. Qu'est-ce que ça implique pour l'ordre de création des ressources ? Est-ce qu'on a eu besoin de le préciser explicitement ?

Question 3

Imagine qu'un collègue reprenne ce projet six mois plus tard. Qu'est-ce qu'il a besoin de faire pour recréer exactement la même infrastructure ? Compare avec ce qui aurait été nécessaire si on avait tout fait à la main (TP 2).

Question 4

On a utilisé access_key = "test" dans le provider. Sur AWS réel, comment Terraform saurait-il quelles credentials utiliser sans les écrire en dur dans le code ?

Corrigé et pistes de réflexion

Question 1 – Différence fondamentale

En TP 2, on a effectué des actions (clics, commandes) dans un ordre précis. En TP 3, on a décrit un état souhaité et Terraform a déterminé lui-même les actions à exécuter pour y arriver. C'est le passage du mode impératif ("faire X puis Y puis Z") au mode déclaratif ("voici ce que je veux, débrouille-toi"). La conséquence : le fichier main.tf est à la fois la documentation et le moyen de déploiement — il dit quoi, pas comment.

Question 2 – Dépendances implicites

En référençant aws_s3_bucket.site.id, Terraform sait que l'objet dépend du bucket. Il construira automatiquement un graphe de dépendances et créera le bucket avant les objets — sans qu'on ait eu à l'écrire explicitement. C'est une des forces de Terraform : les dépendances se déduisent des références. On peut aussi forcer une dépendance explicite avec depends_on si nécessaire.

Question 3 – Reproductibilité

Avec Terraform : git clone du projet + terraform init + terraform apply. Trois commandes, résultat identique garanti. Sans IaC : il faudrait un document de procédure (souvent incomplet ou obsolète), refaire chaque étape à la main, et espérer n'avoir rien oublié. C'est exactement pourquoi les équipes DevOps versionnent l'infrastructure dans Git avec l'application.

Question 4 – Credentials en production

Sur AWS réel, on ne met jamais les credentials en dur dans le code (risque de les commiter dans Git). Terraform les cherche dans l'ordre suivant : variables d'environnement (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY), profils AWS CLI (~/.aws/credentials), rôle IAM attaché à la machine (en production sur EC2 ou en CI/CD). La bonne pratique est d'utiliser des rôles IAM — pas de secrets à gérer, rotation automatique.

☁️ Variante – Déployer sur AWS réel

Le TP complet a été réalisé sur LocalStack. Voici ce qui change pour déployer exactement la même infrastructure sur un vrai compte AWS.

A. Configurer les credentials AWS

Sur AWS réel, Terraform lit les credentials depuis les variables d'environnement ou le fichier de configuration AWS CLI. Ne jamais les écrire dans le code.

1
Via variables d'environnement
# Windows PowerShell
$env:AWS_ACCESS_KEY_ID     = "AKIAIOSFODNN7EXAMPLE"
$env:AWS_SECRET_ACCESS_KEY = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
$env:AWS_DEFAULT_REGION    = "eu-west-3"

# macOS / Linux
export AWS_ACCESS_KEY_ID="AKIAIOSFODNN7EXAMPLE"
export AWS_SECRET_ACCESS_KEY="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
export AWS_DEFAULT_REGION="eu-west-3"
Récupérer ces valeurs dans la console AWS : IAM → Users → ton utilisateur → Security credentials → Create access key.
2
Via AWS CLI (profil nommé — recommandé)
aws configure --profile formation

AWS CLI demande successivement : Access Key ID, Secret Access Key, région par défaut (eu-west-3), format de sortie (json).

Les credentials sont stockés dans ~/.aws/credentials. Pour utiliser ce profil avec Terraform :

# Windows PowerShell
$env:AWS_PROFILE = "formation"

# macOS / Linux
export AWS_PROFILE="formation"
C'est la méthode recommandée : les credentials ne transitent jamais dans des variables ou des fichiers de code.

B. Modifier le provider dans main.tf

Remplacer le bloc provider "aws" du TP LocalStack par celui-ci :

provider "aws" {
  region = "eu-west-3"   # Paris — adapter selon le compte

  # Pas de access_key / secret_key en dur
  # Terraform les lit depuis les variables d'environnement
  # ou depuis ~/.aws/credentials (profil AWS_PROFILE)

  # Pas de skip_credentials_validation
  # Pas de s3_use_path_style
  # Pas de endpoints personnalisés
}
Ne jamais committer des credentials AWS dans Git. Si access_key ou secret_key apparaissent dans un fichier versionné, GitHub les détecte et AWS les révoque automatiquement — mais le risque d'exploitation entre la création et la révocation est réel.

C. Nommage du bucket — contrainte de production

Sur AWS réel, le nom du bucket doit être unique mondialement. mon-site-tf-demo est probablement déjà pris. Utiliser un nom suffisamment spécifique :

resource "aws_s3_bucket" "site" {
  bucket = "mon-site-tf-demo-2cld3-<tes-initiales>"
}

Mettre à jour le nom dans la ressource aws_s3_object et dans l'output frontend_url en conséquence.

D. Accès public — étape supplémentaire sur AWS réel

Contrairement à LocalStack, AWS bloque par défaut tout accès public. Il faut le désactiver explicitement dans Terraform, puis ajouter une Bucket Policy :

# Désactiver le blocage des accès publics
resource "aws_s3_bucket_public_access_block" "site" {
  bucket = aws_s3_bucket.site.id

  block_public_acls       = false
  block_public_policy     = false
  ignore_public_acls      = false
  restrict_public_buckets = false
}

# Autoriser la lecture publique des objets
resource "aws_s3_bucket_policy" "site" {
  bucket = aws_s3_bucket.site.id
  depends_on = [aws_s3_bucket_public_access_block.site]

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = "*"
      Action    = "s3:GetObject"
      Resource  = "${aws_s3_bucket.site.arn}/*"
    }]
  })
}

E. URL du site sur AWS réel

Sur AWS réel, l'URL d'un objet S3 suit ce format :

https://<bucket-name>.s3.<region>.amazonaws.com/index.html

Ajouter cet output dans main.tf pour l'afficher après le déploiement :

output "frontend_url_aws" {
  value = "https://${aws_s3_bucket.site.bucket}.s3.${var.aws_region}.amazonaws.com/index.html"
}

📦 Annexe – Providers Terraform

Un provider est un plugin Terraform qui sait parler à une API spécifique. Il traduit les blocs resource du code HCL en appels d'API réels (AWS, Azure, GCP, GitHub, Kubernetes…). Terraform ne sait rien d'AWS nativement — c'est le provider hashicorp/aws qui contient toute la connaissance des ressources et de leurs paramètres.

A. D'où viennent les providers ?

Les providers sont publiés sur le Terraform Registry : registry.terraform.io. Terraform les télécharge automatiquement lors du terraform init — aucune installation manuelle requise.

B. Déclarer les providers requis

Dans le bloc terraform { required_providers { ... } } en haut du main.tf :

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"   # registre/auteur/nom
      version = "~> 5.0"          # ~> 5.0 = >=5.0 et <6.0
    }
    archive = {
      source  = "hashicorp/archive"
      version = "~> 2.0"
    }
  }
}
Contraintes de version :
  • ~> 5.0 — versions 5.x uniquement (patch autorisé, majeur bloqué)
  • >= 5.0 — 5.0 ou supérieur, sans limite haute
  • = 5.3.0 — version exacte uniquement
  • > 5.0 — strictement supérieur à 5.0
La contrainte ~> 5.0 est recommandée : elle protège contre les breaking changes de version majeure tout en permettant les correctifs.

C. terraform init — téléchargement des providers

terraform init

Cette commande :

  1. Lit le bloc required_providers
  2. Télécharge les plugins depuis registry.terraform.io dans .terraform/providers/
  3. Crée (ou met à jour) le fichier .terraform.lock.hcl qui verrouille les versions exactes
À relancer obligatoirement après avoir ajouté un nouveau provider ou modifié une contrainte de version.

D. Le fichier .terraform.lock.hcl

Ce fichier est créé automatiquement par terraform init. Il verrouille les versions exactes des providers installés :

provider "registry.terraform.io/hashicorp/aws" {
  version     = "5.54.1"
  constraints = "~> 5.0"
  hashes = [
    "h1:...",   # empreinte pour vérification d'intégrité
  ]
}
À committer dans Git (contrairement au dossier .terraform/). Il garantit que tous les membres de l'équipe utilisent exactement la même version du provider, évitant les différences de comportement entre machines.

E. Vérifier les providers installés

terraform providers

Affiche l'arbre des providers requis par le projet courant et leurs sources.

terraform version

Affiche la version de Terraform ET la liste des providers actuellement installés dans .terraform/.

F. Mettre à jour un provider

terraform init -upgrade

Force la mise à jour vers la dernière version compatible avec la contrainte déclarée dans required_providers, et met à jour le .terraform.lock.hcl.

Ne pas confondre terraform init -upgrade (met à jour les providers) avec terraform apply (met à jour l'infrastructure). Ce sont deux niveaux distincts.
